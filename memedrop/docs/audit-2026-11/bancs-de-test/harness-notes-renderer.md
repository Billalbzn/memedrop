## run_command

Writes behavior.json, behavior-android.json and perf.json. Takes about 7 min: WebM recording about 7 s, Electron behaviour about 55 s, Android about 12 s, perf about 6 min. Options: --only=behavior,android,perf  --filter=<substr,...>  --perf-reps=3  --perf-window=4000  --perf-headless (default is headed under an auto-started Xvfb)  --no-trace  --list (prints every scenario with its description). Helpers: node .../renderer-harness/show.js <out-dir>/behavior.json [scenario...] [--dom] gives a readable transcript. node .../renderer-harness/probe-bugs.js <memedrop-root> [--runs=6] collects the evidence for the timing-dependent bugs, which cannot go in the deterministic transcripts.

## compare_command
node /tmp/claude-0/-home-user-memedrop/065ca17e-4939-5472-b348-276c03e80469/scratchpad/renderer-harness/compare.js <dirA> <dirB> [--show-soft] [--all-metrics] [--threshold=10] [--max=40]    (example: node .../renderer-harness/compare.js /tmp/claude-0/-home-user-memedrop/065ca17e-4939-5472-b348-276c03e80469/scratchpad/renderer-harness/baseline <out-new>). It deep-diffs both behaviour transcripts step by step. HARD differences are anything observable. Soft differences are keys prefixed "~" (values that depend on Math.random: drop positions, rain mix, rain count mid-fall) and bridge calls emitted at the same fake millisecond in a different order. Exit code is 1 when there is at least one HARD difference. It then prints the perf table for each scenario (medians A→B, Δ, Δ%, flagged "better"/"WORSE" beyond ±threshold; frame counts are informational only). It also warns when the harness fingerprint or the perf settings differ between the two directories.

## limitations
Validation: the harness was run against altered copies of the code; every altered copy was flagged as a HARD difference:
- MAX_CONCURRENT 6→5
- the double-speech guard removed (speech.length 1→2)
- HOVER_MARGIN 14→30
- android-shim MARGIN 18→20 (rect sizes change)
- `defer` added to the overlay.js script tag, so the Gradle-style shim injection silently fails and Android errors are reported
- the 60 px drop-shadow removed (computed filter diff)
A pure refactor (functions renamed, hit-test loop rewritten) gave 0 differences.
Determinism: the final harness produced 4 byte-identical runs (the baseline plus 3 verification runs, one under concurrent CPU load). The previous harness revision also gave 4 identical runs.

Limitations:
(1) Environment-bound baseline: Chromium 153 headless-shell or Xvfb on Linux, not Electron on Windows or the Android WebView. Fonts, emoji and media stack differ, so layout sizes (caption heights, toast widths) are only comparable between runs on the same machine and browser. Re-record the baseline when the environment changes; the harness fingerprint in meta catches harness edits.
(2) CSS animations are pinned to their settled state, so behaviour during entry and exit animations is not in the transcripts. Bugs 2-3 rely on probe-bugs.js, which is non-deterministic by design.
(3) Electron and main-process semantics are emulated:
- cursor IPC is delivered at harness-chosen moments rather than by a 16 ms poll
- click-through is modelled by not delivering mousedown/up while setIgnoreMouse(true)
- there is no real transparent window
Android:
- touch handles are not emulated beyond __mdDropCtl.move/close
- MDOverlay is a plain JS object
(4) Media runs in real time. WebM clips are recorded per run with MediaRecorder (content about 1.6/3.3/6.6 s; declared durations patched longer: 2/4/8 s, so 'loadedmetadata' is not racy), and durations are never written to transcripts. A long video, live-video-volume or ended-path scenario needs the machine to keep up with real-time playback. Timeouts appear as notes and as diffs. The 10 s audio hard cap is not exercised.
(5) Because of bug 1, the live 'volume' scenario uses a video that never loads; a playing video's live volume is only probed.
(6) Positions and rain parameters depend on the order in which the code consumes Math.random. They are soft ("~") with hard invariants (bounds, counts, zone violations, hole target), but an optimisation that draws randoms differently will show soft diffs.
(7) Inline styles and DOM structure are recorded. Moving a style from inline to a CSS class, driving the life bar with WAAPI instead of a transition, or drawing the rain on a canvas will show HARD diffs that need human review.
(8) Perf numbers are real-time and noisy: medians of 3, other agents shared the 4 vCPUs. The trace pass adds overhead, so trace.* numbers are only comparable with trace.* numbers. Headed Xvfb presentation is not Windows layered-window presentation. With one drop on screen the GPU process is saturated, so judge with trace.vizPerFrame_ms, trace.cpuPerFrame_ms and frames, not only cpu.gpu_ms.
(9) Not covered: settings.html/settings.js, main.js itself, Kotlin code, Android performance (android-shim reports every 120 ms forever; the transcripts show idleTimers=1).
(10) The harness depends on Playwright clock internals (window.__pwClock.countTimers for idleTimers; pauseAt replay so ticks start at 0) as found in Playwright 1.63.
(11) A cwd slip briefly created two empty/stray files (probe-final.json, probe-final.err) in /home/user/memedrop/memedrop. They were deleted within a minute; git status is clean and nothing else under /home/user/memedrop was touched.
